# access-node-compose-api

Small HTTP service that publishes the container image versions of a DOME
access-node environment, as rendered from
[`DOME-Marketplace/dome-gitops`](https://github.com/DOME-Marketplace/dome-gitops).

It is consumed by
[`DOME-Marketplace/access-node-compose`](https://github.com/DOME-Marketplace/access-node-compose),
which installs the access-node with Docker Compose.

One instance runs per environment (sbx, dev, dev2, production). Each instance
only knows its own environment, through the chart path it is configured with.

## How it works

1. A background task keeps a shallow, sparse clone of the gitops repository
   (only `ACCESS_NODE_CHART_PATH`) and fetches it every
   `REFRESH_INTERVAL_SECONDS`.
2. When the hash of the chart tree changes, the chart is copied to a temporary
   directory and rendered with `helm dependency build` + `helm template`.
3. The images of the containers of every `Deployment` are mapped to the
   service keys of `compose-template.yaml` (`DESMOS_IMAGE`,
   `TM_FORUM_API_ACCOUNT_IMAGE`, ...).
4. The result replaces the previous one atomically. If a refresh fails, the
   last valid result keeps being served: responses are never partial.

The service only reads the public gitops repository. It does not talk to the
Kubernetes API.

## API

All endpoints live under `{BASE_PATH}/v1`. Nothing is served outside that
prefix, because the public host is shared with other applications.

| Endpoint | Description |
|---|---|
| `GET {BASE_PATH}/v1/versions` | `text/plain` list of `KEY=image` lines, see below |
| `GET {BASE_PATH}/v1/health` | Liveness: `200` while the process is running |
| `GET {BASE_PATH}/v1/ready` | Readiness: `503` until the first successful render, then `200`. Also reports the running service `version` |
| `GET {BASE_PATH}/v1/docs` | Swagger UI (assets loaded from a public CDN) |
| `GET {BASE_PATH}/v1/openapi.json` | OpenAPI schema |

### `GET /v1/versions`

```
# Generated by access-node-compose-api from dome-gitops
# chart: ionos_prd/marketplace/access-node
# gitops-commit: 0123456789abcdef0123456789abcdef01234567
# generated-at: 2026-11-06T10:15:00Z
# missing: TM_FORUM_API_PARTY_ROLE_IMAGE
TM_FORUM_API_ACCOUNT_IMAGE=...
DESMOS_IMAGE=...
```

- Lines are sorted by key. Comment lines start with `#`.
- Services not deployed by the chart are omitted and listed in `# missing:`.
  Clients are expected to fall back to their own static values for them.
- `503` with `Retry-After` until the first render has succeeded.
- Every response carries an `ETag`; send it back in `If-None-Match` to get a
  `304 Not Modified` when nothing changed.

### Authentication

Disabled by default. If `API_KEY` is set, `/v1/versions` requires the header
`X-API-Key: <key>`. Health, readiness and docs stay open.

## Configuration

| Variable | Default | Description |
|---|---|---|
| `ACCESS_NODE_CHART_PATH` | *(required)* | Chart path in the gitops repo, e.g. `ionos_sbx/marketplace/access-node` |
| `GITOPS_REPO_URL` | `https://github.com/DOME-Marketplace/dome-gitops.git` | Cloned anonymously over HTTPS |
| `GITOPS_BRANCH` | `main` | |
| `REFRESH_INTERVAL_SECONDS` | `300` | Interval between fetches (minimum 30) |
| `WORK_DIR` | `/work` | Clone and temporary render directories |
| `BASE_PATH` | *(empty)* | Path prefix of every route, e.g. `/access-node-compose-api` |
| `PORT` | `8080` | |
| `API_KEY` | *(empty)* | Enables API-key authentication when set |
| `HOME`, `HELM_CACHE_HOME`, `HELM_CONFIG_HOME`, `HELM_DATA_HOME` | under `/work` in the image | Must be writable |

The reverse proxy must forward `{BASE_PATH}/...` **without stripping** the prefix.

## Build the image

The image runs as UID/GID `10001` and supports a read-only root filesystem:
it only writes to `/work` and `/tmp`, which must be writable volumes.
It bundles `git` and a pinned `helm` release, whose checksum is verified
at build time (see `HELM_VERSION` in the [Dockerfile](Dockerfile)).

The image tag is the application version, `X.Y.Z` without the `v` prefix.
It must match `__version__` in
[`src/access_node_compose_api/__init__.py`](src/access_node_compose_api/__init__.py).

```bash
IMAGE=ghcr.io/dome-marketplace/access-node-compose-api
VERSION=$(sed -n 's/^__version__ = "\(.*\)"/\1/p' src/access_node_compose_api/__init__.py)

docker build --platform linux/amd64 -t "$IMAGE:$VERSION" .
```

`--platform linux/amd64` matches the DOME clusters. It is only needed when
building on another architecture (e.g. Apple Silicon), but is harmless otherwise.

### Run it locally

```bash
docker run --rm -p 8080:8080 --read-only --user 10001:10001 \
  --tmpfs /work:uid=10001,gid=10001 --tmpfs /tmp \
  -e ACCESS_NODE_CHART_PATH=ionos_sbx/marketplace/access-node \
  -e BASE_PATH=/access-node-compose-api \
  "$IMAGE:$VERSION"

curl -i localhost:8080/access-node-compose-api/v1/versions
```

- Docker mounts a `--tmpfs` as `root 755`, hence the `uid`/`gid` options on
  `/work`. On Kubernetes an `emptyDir` is writable by any user.
- If port 8080 is taken, change only the host side: `-p 8083:8080`.
- The first render needs outbound access to GitHub and to the Helm
  repositories of the chart dependencies, and takes a few seconds.
- Swagger UI: <http://localhost:8080/access-node-compose-api/v1/docs>.

Always test the image locally, against the chart of every environment you are
going to deploy (`ionos_sbx`, `ionos_dev`, `ionos_dev2`, `ionos_prd`), before
publishing it.

## Publish to the registry (ghcr.io)

Images are published as `ghcr.io/dome-marketplace/access-node-compose-api:X.Y.Z`.
A version tag is **immutable**: never push a different image under a tag that
was already published. Bump the version instead.

### Release checklist

1. Set the new version in `src/access_node_compose_api/__init__.py` and merge
   it to `main`.
2. Build and test the image locally (see above).
3. Tag the commit: `git tag vX.Y.Z && git push origin vX.Y.Z`.
4. Push the image (see below).

> An automated release workflow (build and push on `vX.Y.Z` tags, using the
> repository `GITHUB_TOKEN`) is planned. Once it exists, step 4 is done by CI
> and no personal credentials are needed.

### Login

ghcr.io does not accept your GitHub password. Use your GitHub **username** and
a **personal access token (classic)**:

1. GitHub → *Settings* → *Developer settings* → *Personal access tokens* →
   *Tokens (classic)* → *Generate new token (classic)*.
2. Select the `write:packages` scope (it includes `read:packages`). Give it a
   short expiration: it is only needed for the push.
3. If the DOME-Marketplace organization enforces SAML SSO, click
   *Configure SSO* next to the token and authorize it for the organization.
4. You need permission to create packages in the organization, or write access
   to the `access-node-compose-api` package if it already exists.

Log in without leaving the token in your shell history:

```bash
read -rs CR_PAT    # paste the token, then press Enter
echo "$CR_PAT" | docker login ghcr.io -u <your-github-username> --password-stdin
unset CR_PAT
```

Fine-grained tokens are not supported for pushing to ghcr.io. Never commit a
token, and log out when done.

### Push

```bash
docker push "$IMAGE:$VERSION"
docker logout ghcr.io
```

### First publish only: make the package public

A new package on ghcr.io is private, so the clusters cannot pull it without an
image pull secret. After the first push, an organization owner (or a package
admin) must:

1. Open the organization page → *Packages* → `access-node-compose-api` →
   *Package settings*.
2. Under *Danger Zone*, choose *Change visibility* → *Public*.
3. Check that the package is linked to this repository. The
   `org.opencontainers.image.source` label of the image normally links it
   automatically.

Verify an anonymous pull works:

```bash
docker logout ghcr.io
docker pull "$IMAGE:$VERSION"
```

## Deploy with dome-gitops

The service is deployed by Argo CD from
[`DOME-Marketplace/dome-gitops`](https://github.com/DOME-Marketplace/dome-gitops),
one instance per environment, in the `marketplace` namespace.

| Environment | Manifests directory | Argo CD Application | `ACCESS_NODE_CHART_PATH` |
|---|---|---|---|
| sbx | `ionos_sbx/marketplace/access-node-compose-api/` | `applications_sbx/marketplace/access-node-compose-api.yaml` | `ionos_sbx/marketplace/access-node` |
| dev | `ionos_dev/marketplace/access-node-compose-api/` | `applications_dev/marketplace/access-node-compose-api.yaml` | `ionos_dev/marketplace/access-node` |
| dev2 | `ionos_dev2/marketplace/access-node-compose-api/` | `applications_dev2/marketplace/access-node-compose-api.yaml` | `ionos_dev2/marketplace/access-node` |
| prd | `ionos_prd/marketplace/access-node-compose-api/` | `applications_prd/marketplace/access-node-compose-api.yaml` | `ionos_prd/marketplace/access-node` |

Each manifests directory contains:

- `deployment.yaml`: 1 replica, image `ghcr.io/dome-marketplace/access-node-compose-api:X.Y.Z`,
  the environment variables of the [Configuration](#configuration) section,
  probes on `{BASE_PATH}/v1/health` (liveness) and `{BASE_PATH}/v1/ready`
  (readiness), `readOnlyRootFilesystem: true`, `emptyDir` volumes on `/work`
  and `/tmp`, `automountServiceAccountToken: false`, limits 500m/512Mi.
- `service.yaml`: ClusterIP `access-node-compose-api`, port `8080`.

The public route (`https://<portal host>/access-node-compose-api/*` →
`access-node-compose-api.marketplace:8080`) is configured on the Caddy
reverse proxy of each environment, outside this repository. Caddy must
forward the path **without stripping** `/access-node-compose-api`.

> The environment variables are the contract between this service and the
> deployment. If one is added or renamed here, update the `deployment.yaml`
> of every environment.

### Add a new environment

Start from sbx, which is the reference deployment.

1. **The image must already be published and public** (see above). If Argo CD
   syncs a deployment whose image does not exist, the pod stays in
   `ImagePullBackOff`.
2. Test the image locally with the chart of the target environment, for
   example:
   ```bash
   docker run --rm -p 8080:8080 --read-only --user 10001:10001 \
     --tmpfs /work:uid=10001,gid=10001 --tmpfs /tmp \
     -e ACCESS_NODE_CHART_PATH=ionos_prd/marketplace/access-node \
     -e BASE_PATH=/access-node-compose-api \
     "$IMAGE:$VERSION"
   ```
   With `ionos_prd`, `/v1/versions` currently reports
   `# missing: TM_FORUM_API_PARTY_ROLE_IMAGE`: this is expected.
3. In a branch of dome-gitops, copy the sbx files, replacing `<env>` with
   `dev`, `dev2` or `prd`:
   ```bash
   mkdir -p ionos_<env>/marketplace/access-node-compose-api
   cp ionos_sbx/marketplace/access-node-compose-api/*.yaml ionos_<env>/marketplace/access-node-compose-api/
   cp applications_sbx/marketplace/access-node-compose-api.yaml applications_<env>/marketplace/
   ```
4. Edit the copies:
   - `ionos_<env>/.../deployment.yaml`: set `ACCESS_NODE_CHART_PATH` to
     `ionos_<env>/marketplace/access-node`. Keep `BASE_PATH` and the probe paths
     consistent with the Caddy route of that environment.
   - `applications_<env>/marketplace/access-node-compose-api.yaml`: set
     `spec.source.path` to `ionos_<env>/marketplace/access-node-compose-api`.
5. Check that nothing still points to sbx:
   ```bash
   grep -rn sbx ionos_<env>/marketplace/access-node-compose-api applications_<env>/marketplace/access-node-compose-api.yaml
   ```
6. Open a pull request to dome-gitops and merge it. The Application has
   automated sync, so Argo CD creates the resources after the merge.
7. Ask for the Caddy route of the environment.
8. Verify (see [Verify a deployment](#verify-a-deployment)).

Suggested order: sbx → dev → dev2 → prd, moving to the next environment only
after the previous one has been verified.

### Upgrade to a new version

1. Publish the new image (see [Publish to the registry](#publish-to-the-registry-ghcrio)).
2. In dome-gitops, change the `image:` tag in
   `ionos_<env>/marketplace/access-node-compose-api/deployment.yaml`, one
   environment at a time, in the same order (sbx first, prd last).
3. Merge; Argo CD rolls out the new pod. Until the new pod is ready, the old
   one keeps serving.

To roll back, revert the tag change in dome-gitops.

### Verify a deployment

With `kubectl` access to the cluster of the environment:

```bash
kubectl -n marketplace get pods -l app.kubernetes.io/name=access-node-compose-api
kubectl -n marketplace rollout status deployment/access-node-compose-api
kubectl -n marketplace logs deployment/access-node-compose-api

kubectl -n marketplace port-forward svc/access-node-compose-api 8083:8080
curl -s localhost:8083/access-node-compose-api/v1/ready
curl -s localhost:8083/access-node-compose-api/v1/versions
```

The pod is `Ready` once the first render has succeeded, usually within a few
seconds of startup. If it stays not ready, `/v1/ready` reports the cause in
`last_error`. Its `version` field shows which release is running:

```bash
curl -s localhost:8083/access-node-compose-api/v1/ready | jq -r .version
```

Through the public route (sbx):

```bash
curl -i https://tmf-test.dome-marketplace-sbx.org/access-node-compose-api/v1/versions
```

Check that:

- `# chart:` shows the chart path of the right environment;
- `# gitops-commit:` matches a recent commit of dome-gitops `main`;
- `# missing:` lists only the services that are really not deployed in that
  environment.
